Reasoner 01 / Rules

First, derive tower health from connected observations.

telco_base_ontology.py / deployed definitions
model.define(
    CellTower.avg_packet_loss(
        aggs.avg(NetworkPerformance.packet_loss_pct)
        .where(NetworkPerformance.tower == CellTower)
        .per(CellTower)
    )
)
model.define(
    CellTower.avg_health_score(
        aggs.avg(EquipmentHealth.health_score)
        .where(
            EquipmentHealth.equipment == NetworkEquipment,
            NetworkEquipment.tower == CellTower,
        )
        .per(CellTower)
    )
)

What the model computes

Performance to towerAverage packet loss is derived from related network-performance observations.
Health to equipment to towerEquipment health rolls up through installed equipment to its tower.
These are reusable ontology properties. The policy rule and agent can read the same derived values.

Reasoner 02 / Predictive

Features are typed, and the training label is kept out.

run_predictive_failure.py / abridged feature configuration
equipment_df["AT_RISK"] = (
    equipment_df["STATUS"].isin(["FAILING", "WARNING"]).astype(int)
)
pt = PropertyTransformer(
    drop=[
        NetworkEquipment.status,
        CellTower.avg_health_score,
    ],
    category=[
        NetworkEquipment.equipment_type,
        ModelAdvisory.advisory_type,
    ],
    continuous=[
        EquipmentHealth.failure_rate,
        EquipmentHealth.health_score,
        ModelAdvisory.severity,
    ],
    integer=[EquipmentHealth.mtbf_hours, CellTower.capacity_gbps],
)

Design choices

SupervisionCurrent WARNING/FAILING status supplies the synthetic positive label.
Leakage guardEquipment status is excluded from model features because it defines the label.
Typed featuresCategorical, continuous, and integer properties are encoded for the connected graph.
This is an at-risk status proxy, not a calibrated future-failure forecast.

Reasoner 03 / Graph

Construct the call graph, then run PageRank.

run_graph_impact.py / directed graph and centrality
call_graph = Graph(
    model,
    directed=True,
    weighted=False,
    node_concept=Subscriber,
    aggregator="sum",
)
cdr = CallDetailRecord.ref()
caller = Subscriber.ref()
callee = Subscriber.ref()
model.where(
    cdr.caller(caller),
    cdr.callee(callee),
).define(call_graph.Edge.new(src=caller, dst=callee))
call_graph.Node.influence_score = call_graph.pagerank()

What this graph means

NodesSubscribers are the graph's node concept.
EdgesEach call record creates a directed caller-to-callee edge.
CentralityPageRank assigns subscriber influence; it does not by itself measure tower value.
Reasoner 03 / Graph

Link routed calls back to towers and customer impact.

run_graph_impact.py / tower-level impact derivation
model.define(
    CellTower.weighted_impact(
        aggs.sum(Subscriber.customer_value)
        .where(
            CallDetailRecord.routed_through(CellTower),
            CallDetailRecord.caller(Subscriber),
            Subscriber.status == "ACTIVE",
        )
        .per(CellTower)
    )
)

The decision input

Call-weighted valueEach active caller's value contributes once per routed call record, so repeated calls count repeatedly.
Separate PageRank rollupThe job also sums caller influence over routed calls as weighted_pagerank.
The optimizer uses weighted_impact. PageRank is available for explanation, but is not a multiplier in the current objective.

Reasoner 05 / Prescriptive

Make budget, crew, and exclusivity hard constraints.

run_optimization.py / constraint expressions (shared scope shown once)
scope = model.where(
    TowerUpgradeOption.tower == CellTower,
    CellTower.is_critical_restore(),
)
problem.satisfy(
    scope.require(aggs.sum(TowerUpgradeOption.selected).per(CellTower) <= 1)
)
problem.satisfy(
    scope.require(
        aggs.sum(TowerUpgradeOption.selected * TowerUpgradeOption.cost)
        <= budget_usd
    )
)
problem.satisfy(
    scope.require(
        aggs.sum(TowerUpgradeOption.selected * TowerUpgradeOption.install_weeks)
        <= INSTALL_WEEKS_BUDGET
    )
)

Three limits

One tier per towerThe sum of selected tier options is at most one for each tower.
Budget is a parameterbudget_usd can change for a live scenario; the saved baseline uses $5M.
Install capacityThe current crew limit is 200 total weeks.
The source repeats the same model.where(...) scope inside each constraint; it is factored here for slide legibility.
Reasoner 05 / Prescriptive

Optimize the portfolio, then inspect the solver status.

run_optimization.py / objective and solve
problem.maximize(
    aggs.sum(
        TowerUpgradeOption.selected
        * TowerUpgradeOption.capacity_increase_gbps
        * CellTower.weighted_impact
        * CellTower.failure_intensity
    ).where(
        TowerUpgradeOption.tower == CellTower,
        CellTower.is_critical_restore(),
    )
)
problem.solve("highs")
status = problem.solve_info().termination_status

The Trust Boundary

What is actually validated, deterministic, and traceable?

Demonstrated in this snapshot

01

Named inputs. The curated query reads the deployed ontology and named RESULTS tables, not an agent-generated calculation.

02

Reconciled plan. The query rejects a mismatch in selected row count, cost, install weeks, or capacity against RESTORE_PLAN.

03

Fixed result. Repeated reads of unchanged materialized tables return the same plan data. The stored solver status is OPTIMAL.

Do not claim as guaranteed yet

01

Agent prose. A free-form answer can omit a row or invent a cause; compare it with tool output and escalate unsupported claims.

02

Retraining. The synthetic-label GNN is a risk proxy; retraining can change scores and the downstream plan.

03

Row lineage. This demo names source tables and jobs but does not persist a versioned, end-to-end row-level provenance record.

For a production guarantee, add pinned input versions and trace IDs around this validated decision result, then evaluate the agent's rendering.

From Decision to Answer

Make the agent's recommendation inspectable.

The ontology and reasoners compute a constrained plan. The agent explains it using curated results that can be checked against the stored decision.

Decision result

Inputs: named Snowflake sources, operational rules, and materialized reasoner outputs.
Output: selected tower tiers, totals, solver status, and supporting signals.
Checks: selected rows reconcile with budget, crew weeks, and restored capacity.

Agent answer checks

Trace: which curated query ran and what rows it returned.
Evaluate: completeness, arithmetic, unsupported claims, latency, and cost.
Escalate: review answers when evidence is missing or a result fails its checks.

The demo reconciles a stored plan. Production-grade reproducibility also needs pinned snapshots, trace IDs, and versioned row-level lineage.
